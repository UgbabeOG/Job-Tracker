# JobTrack — REST API Contract

**Version:** 1.0  
**Base URL (local):** `http://localhost:8080`  
**API prefix:** `/api`  
**Content type:** `application/json`  
**Backend:** Go with `net/http`  
**Database:** SQLite

## 1. General API Rules

### Request format

All request bodies must be valid JSON.

Requests containing JSON must use:

`Content-Type: application/json`

### Response format

Successful responses return JSON unless the endpoint explicitly specifies an empty response.

Error responses use the common error structure defined in Section 8.

### Resource identifiers

Job IDs are strings generated by the backend. Clients must treat IDs as opaque values and must not generate IDs themselves.

### Dates

Dates use ISO 8601 calendar-date format:

`YYYY-MM-DD`

Example: `2026-10-19`

Dates are calendar dates, not timestamps. Do not convert them into UTC timestamps when comparing deadlines.

### Application statuses

The only valid values are:

- `Saved`
- `Applied`
- `Interview`
- `Offer`
- `Rejected`

The spelling and capitalization must be consistent across the frontend, backend, and database.

### Local development

The frontend and backend may run on different ports during development. Configure the frontend API base URL and enable restricted CORS for the local frontend origin when necessary.

CORS is not a substitute for authentication or authorization.

## 2. Job Application Data Model

### Job object

```json
{
  "id": "job-001",
  "company": "Example Technologies",
  "job_title": "Junior Backend Developer",
  "job_url": "https://example.com/jobs/1",
  "date_applied": "2026-10-19",
  "deadline": "2026-10-25",
  "status": "Applied",
  "notes": "Follow up next week",
  "created_at": "2026-10-19T09:30:00Z",
  "updated_at": "2026-10-19T09:30:00Z"
}
```

### Field definitions

| Field | Type | Required in create request | Description |
|---|---|---|---|
| `id` | string | No | Generated by the backend |
| `company` | string | Yes | Employer name |
| `job_title` | string | Yes | Position title |
| `job_url` | string or null | No | Vacancy URL |
| `date_applied` | string or null | No | Application date |
| `deadline` | string or null | No | Closing date |
| `status` | string | No | Defaults to `Saved` |
| `notes` | string or null | No | Optional notes |
| `created_at` | string | No | Generated timestamp |
| `updated_at` | string | No | Generated timestamp |

For a consistent API, the backend should return optional fields as explicit `null` values rather than sometimes omitting them.

`created_at` and `updated_at` are UTC timestamps in RFC 3339 format. The frontend must display them appropriately and must not use these timestamps to calculate calendar-date deadlines.

## 3. Endpoint: List Applications

**Request**

`GET /api/jobs`

Returns all saved applications.

### Successful response — `200 OK`

```json
{
  "data": [
    {
      "id": "job-001",
      "company": "Example Technologies",
      "job_title": "Junior Backend Developer",
      "job_url": null,
      "date_applied": "2026-10-19",
      "deadline": "2026-10-25",
      "status": "Applied",
      "notes": null,
      "created_at": "2026-10-19T09:30:00Z",
      "updated_at": "2026-10-19T09:30:00Z"
    }
  ]
}
```

When no applications exist, return an empty array:

```json
{
  "data": []
}
```

For the MVP, pagination and advanced filtering are not required.

## 4. Endpoint: Create Application

**Request**

`POST /api/jobs`

### Example request body

```json
{
  "company": "Example Technologies",
  "job_title": "Junior Backend Developer",
  "job_url": "https://example.com/jobs/1",
  "date_applied": "2026-10-19",
  "deadline": "2026-10-25",
  "status": "Applied",
  "notes": "Follow up next week"
}
```

Required fields:

- `company`
- `job_title`

Optional fields:

- `job_url`
- `date_applied`
- `deadline`
- `status`
- `notes`

If `status` is omitted, the backend sets it to `Saved`.

### Successful response — `201 Created`

Return the created job object:

```json
{
  "data": {
    "id": "job-001",
    "company": "Example Technologies",
    "job_title": "Junior Backend Developer",
    "job_url": "https://example.com/jobs/1",
    "date_applied": "2026-10-19",
    "deadline": "2026-10-25",
    "status": "Applied",
    "notes": "Follow up next week",
    "created_at": "2026-10-19T09:30:00Z",
    "updated_at": "2026-10-19T09:30:00Z"
  }
}
```

Validation rules:

- Company and job title must not be empty or whitespace-only.
- Dates must be valid `YYYY-MM-DD` calendar dates or `null`.
- Status must be one of the five permitted values.
- A supplied job URL must be a valid HTTP or HTTPS URL.
- Invalid requests must not create database records.

`GET /api/jobs/{id}`

`GET /api/jobs/job-001`

```json
{
  "data": {
    "id": "job-001",
    "company": "Example Technologies",
    "job_title": "Junior Backend Developer",
    "job_url": null,
    "date_applied": "2026-10-19",
    "deadline": "2026-10-25",
    "status": "Applied",
    "notes": null,
    "created_at": "2026-10-19T09:30:00Z",
    "updated_at": "2026-10-19T09:30:00Z"
  }

```

Return `404 Not Found` if the ID does not exist.

## 6. Endpoint: Update an Application

**Request**

`PATCH /api/jobs/{id}`

PATCH updates only the fields supplied in the request.

### Example request body

```json
{
  "status": "Interview",
  "notes": "Interview scheduled for Friday"
}
```

### Successful response — `200 OK`

Return the complete updated job object inside the `data` property.

### PATCH semantics

- Omitted fields remain unchanged.
- Supplied fields are validated before saving.
- Optional fields can be explicitly set to `null` to clear their existing values.
- Required fields such as `company` and `job_title` cannot be set to empty strings.
- `id`, `created_at`, and `updated_at` cannot be modified by the client.
- `updated_at` is refreshed by the backend after a successful update.
- An empty update object should return `400 Bad Request`.
- An unknown job ID returns `404 Not Found`.

The Go implementation must distinguish an omitted field from an explicitly supplied `null`. A basic struct of ordinary string fields cannot reliably represent all three states. Use pointer fields or a small custom PATCH-field type.

## 7. Endpoint: Delete an Application

**Request**

`DELETE /api/jobs/{id}`

Example:

`DELETE /api/jobs/job-001`

### Successful response — `204 No Content`

Return no response body.

The frontend should remove the deleted record from its local state or refresh the application list.

Return `404 Not Found` if the application does not exist.

The frontend should ask the user for confirmation before making this request.

## 8. Standard Error Response

All API errors must use the same JSON structure.

### Example — `400 Bad Request`

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "The request contains invalid fields.",
    "details": {
      "company": "Company is required."
    }
  }
}
```

Fields:

| Field | Type | Description |
|---|---|---|
| `error.code` | string | Stable machine-readable error code |
| `error.message` | string | Human-readable summary |
| `error.details` | object or null | Optional field-level details |

### HTTP status conventions

| Status | Meaning | Example |
|---|---|---|
| `200` | Successful request | Read or update |
| `201` | Resource created | Create application |
| `204` | Successful request with no body | Delete application |
| `400` | Invalid request | Malformed JSON or invalid fields |
| `404` | Resource not found | Unknown job ID |
| `405` | Method not allowed | Unsupported HTTP method |
| `413` | Request too large | Body exceeds configured limit |
| `415` | Unsupported media type | Non-JSON body on a JSON endpoint |
| `500` | Internal server error | Unexpected database or server failure |

Do not return raw SQL errors or internal stack traces to clients.

## 9. Endpoint: Keyword Matching

**Request**

`POST /api/match`

The endpoint compares a CV's text against a job description and returns a deterministic keyword-overlap result.

### Example request body

```json
{
  "cv_text": "I have experience with Go, REST APIs, SQL and Git.",
  "job_description": "We need a developer with Go, REST API, SQL, Git and Docker experience.",
  "required_keywords": [
    "Go",
    "REST API",
    "SQL",
    "Git",
    "Docker"
  ]
}
```

`cv_text` and `job_description` are required non-empty strings.

`required_keywords` is optional. If provided, it defines the exact keywords to score. If omitted, the backend uses the agreed, documented skill vocabulary to identify candidate keywords from the job description.

### Successful response — `200 OK`

```json
{
  "data": {
    "score": 80,
    "matched_keywords": [
      "Go",
      "REST API",
      "SQL",
      "Git"
    ],
    "missing_keywords": [
      "Docker"
    ],
    "total_keywords": 5
  }
}
```

### Scoring rules

The score is:

`matched unique required keywords / total unique required keywords × 100`

Round the result to the nearest whole number.

Matching must:

- Ignore capitalization differences.
- Trim unnecessary whitespace.
- Avoid counting duplicate required keywords more than once.
- Avoid matching a keyword solely as part of an unrelated longer word.
- Return matched and missing keywords as arrays.
- Use the same normalization rules for every request.

For the MVP, an explicit list of required keywords is the most predictable approach. Automatic keyword extraction should use a fixed, documented vocabulary rather than an undocumented guess about what matters in a job description.

If no valid required keywords are found, return `400 Bad Request` with code `NO_KEYWORDS_FOUND`. Never divide by zero or return a fabricated score.

This endpoint measures keyword overlap, not a candidate's overall suitability for employment.

## 10. Endpoint: Dashboard Statistics

**Request**

`GET /api/dashboard`

### Successful response — `200 OK`

```json
{
  "data": {
    "total_applications": 12,
    "status_counts": {
      "Saved": 3,
      "Applied": 4,
      "Interview": 2,
      "Offer": 1,
      "Rejected": 2
    },
    "upcoming_deadlines": 2,
    "overdue_applications": 1,
    "total_interviews": 2,
    "total_offers": 1
  }
}
```

The numbers above are illustrative.

### Calculation rules

- `total_applications` counts all saved job records.
- `status_counts` includes all five permitted statuses, including zero counts.
- `total_interviews` counts records currently marked `Interview`.
- `total_offers` counts records currently marked `Offer`.
- `upcoming_deadlines` counts active applications with deadlines from today through the next seven calendar days, inclusive.
- `overdue_applications` counts active applications with deadlines before today.
- `Offer` and `Rejected` applications are excluded from upcoming and overdue counts.
- Applications without deadlines are excluded from both deadline counts.

The backend calculates these values from persisted data. The frontend must not invent or independently recalculate the official dashboard totals.

## 11. Health Check

**Request**

`GET /health`

### Successful response — `200 OK`

```json
{
  "status": "ok"
}
```

This endpoint allows developers to verify that the backend server is responding. It does not, by itself, guarantee that every database operation is working.

## 12. Go Implementation Expectations

The backend should:

1. Register the documented routes using `net/http`.
2. Decode and validate incoming JSON.
3. Reject malformed request bodies and unsupported methods.
4. Use parameterized SQL queries for database operations.
5. Generate unique job IDs on the backend.
6. Set appropriate HTTP status codes and JSON content types.
7. Use a consistent JSON error helper.
8. Keep HTTP handlers, data access, and matching logic separated where practical.
9. Limit request-body size and avoid logging CV contents.
10. Include tests for successful requests, invalid input, missing records, and database errors.

Suggested conceptual separation:

- **Handlers:** HTTP requests, responses, and status codes.
- **Repository:** SQLite queries and persistence.
- **Service or domain functions:** validation, deadline calculations, and keyword matching.
- **Models:** request, response, and job data structures.

The team does not need an elaborate framework or complicated dependency-injection architecture for this MVP.

## 13. Frontend Implementation Expectations

The frontend must:

1. Use the agreed API routes and JSON field names.
2. Keep the API base URL configurable for local development.
3. Display loading, empty, success, and error states.
4. Validate forms for usability while relying on the backend for authoritative validation.
5. Refresh or update the UI after successful create, edit, and delete operations.
6. Avoid showing success messages before the API confirms success.
7. Render CV and job-description text safely as text.
8. Keep date-only values in `YYYY-MM-DD` form when submitting them to the API.

Suggested frontend modules:

- API client
- Job application list and form
- Dashboard
- Deadline indicators
- Keyword-matching form and results
- Shared UI components and types

## 14. API Acceptance Tests

Before release, the team must verify the following:

1. `GET /api/jobs` returns an empty array when the database has no jobs.
2. A valid `POST /api/jobs` returns `201` and a generated ID.
3. The created record remains after a backend restart.
4. Missing company or job title returns `400`.
5. An invalid status or date returns `400`.
6. `GET /api/jobs/{id}` returns the correct record.
7. `PATCH /api/jobs/{id}` updates only supplied fields.
8. An explicit `null` clears an optional field.
9. Updating or deleting a nonexistent record returns `404`.
10. `DELETE /api/jobs/{id}` returns `204` with no response body.
11. Keyword matching returns the correct score and arrays.
12. Duplicate keywords do not inflate the score.
13. An empty matching request or zero-keyword result returns `400`.
14. Dashboard counts match the records in the database.
15. Upcoming and overdue deadline counts behave correctly at date boundaries.
16. Malformed JSON produces a structured error instead of crashing the server.
17. The health endpoint responds successfully.

## 15. Change Management

This contract is the agreed interface between frontend and backend.

If a developer needs to change a route, field, response format, or validation rule:

1. Propose the change to the team.
2. Update this document.
3. Get team approval before implementation depends on the change.
4. Update affected code and tests together.
5. Record the change in the relevant GitHub issue or pull request.

The objective is to keep all team members working against one predictable API throughout the seven-day project.
