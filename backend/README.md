# JobTrack Backend

A REST API for managing job applications, built with Go, `net/http`, and SQLite. The backend provides persistent storage and CRUD operations for tracking job applications.

## Features

- Create, retrieve, update, list, and delete job applications.
- Store job application records in SQLite.
- Generate unique job IDs on the backend.
- Validate required fields, application statuses, dates, and job URLs.
- Support partial updates using `PATCH`, including clearing optional fields with explicit `null` values.
- Return consistent JSON error responses.
- Enforce request-body size limits and validate content types.
- Support restricted Cross-Origin Resource Sharing (CORS) for local frontend development.
- Include automated tests for handlers and CORS behavior.

## Technology Stack

- **Language:** Go
- **HTTP server:** `net/http`
- **Database:** SQLite
- **Database driver:** `modernc.org/sqlite`
- **UUID generation:** `github.com/google/uuid`

## Configuration

The application supports the following environment variables.

| Variable                | Default                                       | Description                                      |
| ----------------------- | --------------------------------------------- | ------------------------------------------------ |
| `JOBTRACK_ADDR`         | `:8080`                                       | HTTP server listen address                       |
| `JOBTRACK_DB`           | `jobtrack.db`                                 | SQLite database file path                        |
| `JOBTRACK_CORS_ORIGINS` | `http://localhost:5173,http://127.0.0.1:5173` | Comma-separated list of allowed frontend origins |

### Configure the server

Example for a local development environment:

```bash
export JOBTRACK_ADDR=:8080
export JOBTRACK_DB=jobtrack.db
export JOBTRACK_CORS_ORIGINS=http://localhost:5173
```

Configure `JOBTRACK_CORS_ORIGINS` to match the actual frontend origin, including its scheme, hostname, and port. Only trusted origins should be added.

These environment variables apply to the current shell session.

## Running the API

Start the server:

```bash
go run ./cmd/api
```

By default, the API listens on port `8080`.

Base URL:

```text
http://localhost:8080
```

Health endpoint:

```text
GET http://localhost:8080/health
```

A successful health check returns:

```json

}
```

Keep the server terminal open while making API requests. Press `Ctrl+C` to stop the server.

## API Endpoints

All job endpoints use the `/api/jobs` prefix and accept or return JSON where applicable.

| Method   | Endpoint         | Description                     | Success status   |
| -------- | ---------------- | ------------------------------- | ---------------- |
| `GET`    | `/api/jobs`      | List job applications           | `200 OK`         |
| `POST`   | `/api/jobs`      | Create a job application        | `201 Created`    |
| `GET`    | `/api/jobs/{id}` | Retrieve a single application   | `200 OK`         |
| `PATCH`  | `/api/jobs/{id}` | Partially update an application | `200 OK`         |
| `DELETE` | `/api/jobs/{id}` | Delete an application           | `204 No Content` |

See [`docs/api-contract.md`](docs/api-contract.md) for the approved API contract, request and response examples, and error formats.

## Job Application Fields

| Field          | Type                  | Description                                  |
| -------------- | --------------------- | -------------------------------------------- |
| `id`           | String                | Generated by the backend                     |
| `company`      | String                | Required employer name                       |
| `job_title`    | String                | Required job title                           |
| `job_url`      | String or `null`      | Optional job listing URL                     |
| `date_applied` | Date string or `null` | Application date in `YYYY-MM-DD` format      |
| `deadline`     | Date string or `null` | Application deadline in `YYYY-MM-DD` format  |
| `status`       | String                | Application status; defaults to `Saved`      |
| `notes`        | String or `null`      | Optional notes                               |
| `created_at`   | Timestamp             | Creation timestamp in UTC RFC 3339 format    |
| `updated_at`   | Timestamp             | Last update timestamp in UTC RFC 3339 format |

Allowed statuses:

- `Saved`
- `Applied`
- `Interview`
- `Offer`
- `Rejected`

Date fields use calendar dates rather than timestamps. Optional fields are returned explicitly as `null` when they have no value.

## Example Requests

### List applications

```bash
curl http://localhost:8080/api/jobs
```

### Create an application

```bash
curl -X POST http://localhost:8080/api/jobs \
  -H "Content-Type: application/json" \
  -d '{
    "company": "Example Technologies",
    "job_title": "Junior Backend Developer",
    "job_url": "https://example.com/jobs/1",
    "date_applied": "2026-10-19",
    "deadline": "2026-10-25",
    "status": "Applied",
    "notes": "Follow up next week"
  }'
```

The server generates the application's ID and timestamps. A successful create request returns `201 Created`.

### Retrieve an application

Replace `{id}` with the ID returned by the create request:

```bash
curl http://localhost:8080/api/jobs/{id}
```

### Update an application

```bash
curl -X PATCH http://localhost:8080/api/jobs/{id} \
  -H "Content-Type: application/json" \
  -d '{
    "status": "Interview",
    "notes": "Interview scheduled"
  }'
```

Only supplied fields are updated. Fields that are omitted remain unchanged.

To clear an optional field, explicitly provide `null`:

```bash
curl -X PATCH http://localhost:8080/api/jobs/{id} \
  -H "Content-Type: application/json" \
  -d '{
    "notes": null
  }'
```

### Delete an application

```bash
curl -i -X DELETE http://localhost:8080/api/jobs/{id}
```

A successful delete returns `204 No Content` with no response body.

## Validation and Error Handling

The API validates incoming requests and returns structured JSON errors for invalid requests and other documented failures.

Validation includes:

- Required company and job title.
- Allowed application status values.
- Valid calendar dates in `YYYY-MM-DD` format.
- Optional job URLs using HTTP or HTTPS.
- Valid JSON request bodies.
- Supported request methods and content types.
- Request-body size limits.
- Existing job IDs for read, update, and delete operations.

The API uses the documented HTTP status codes, including `200`, `201`, `204`, `400`, `404`, `405`, `413`, `415`, and `500` where applicable.

## CORS

The API supports restricted CORS for local frontend development.

The default allowed origins are:

```text
http://localhost:5173
http://127.0.0.1:5173
```

To configure a different origin:

```bash
export JOBTRACK_CORS_ORIGINS=http://localhost:3000
```

Multiple origins can be separated by commas:

```bash
export JOBTRACK_CORS_ORIGINS=http://localhost:3000,http://localhost:5173
```

The middleware handles browser preflight requests and restricts allowed origins. CORS is not a substitute for authentication or authorization.

## Database Persistence

Job records are stored in SQLite. By default, the database file is named `jobtrack.db` relative to the application's working directory.

To use a different database location:

```bash
export JOBTRACK_DB=/path/to/jobtrack.db
```

Use a stable database path when running the application so records remain available after a server restart. Keep database files containing real application data out of public repositories.
